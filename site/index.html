Détection d'état

Loom sait si un agent travaille, vous attend ou a terminé.

Les hooks de Claude Code arrivent par loom-hook sur un socket Unix. Pour un agent sans hooks, une heuristique observe le terminal. Une machine à états pure fusionne les deux canaux.

Envoyer un hook

Ces boutons rejouent la table de transitions de Loom, telle qu'elle est écrite dans son réducteur. Défilez : chaque cran envoie un hook.

Fonctionnalités

Tout ce qu'il faut autour d'une session, dans une seule fenêtre.

Loom héberge Claude Code sans le remplacer. Il isole le travail de chaque session, garde ce qu'elle produit et ouvre les outils dont on a besoin à côté d'elle.

Git

Un worktree par session

Chaque session travaille dans son checkout, sur sa branche. Les collisions de noms sont départagées, et Loom refuse de supprimer un worktree qui contient du travail non commité.

Terminal

Persistant, et repris après un crash

Les transcripts s'écrivent en continu, bruts et sans séquences ANSI. Si l'app s'arrête, la session passe interrupted et reprend sous le même identifiant.

interrupted→working
$claude --resume <uuid>
Vue Chat⌘⇧M

La même session, lue comme une conversation

Réponses en Markdown, appels d'outils repliés sur une ligne, demandes de permission en cartes à boutons, images collées ou déposées. Ce que vous écrivez est tapé dans le terminal de la session.

Pull requests

La review complète, sur votre gh

Une inbox « en attente de moi » tous dépôts confondus, le diff côte à côte, le détail des checks CI. Vos commentaires de ligne restent en brouillon et partent en une seule review, avec le verdict. Chaque PR ouverte a son onglet et peut avoir sa session Claude.

Reviews planifiées

Les reviews préparées avant votre arrivée

Un planning, un projet, une requête GitHub, un maximum par passage. À l'heure dite, Loom ouvre un onglet par PR, lance sa session de review et importe le rapport : résumé, commentaires en attente sur les lignes, verdict suggéré. Vous relisez, corrigez, envoyez.

Navigateur de l'agent

Chaque session pilote son propre navigateur

À côté du terminal, sur un profil isolé par projet : jamais vos cookies. Chromium sans fenêtre quand Loom en trouve un, WebKit sinon. L'agent le pilote par vingt outils MCP au format de Playwright MCP.

Onglet Git

Le diff en pleine largeur

À gauche, Changes ou History. À droite, le diff en couleurs du fichier ou du commit choisi. Commit, push, review et PR tiennent sur une ligne.

Usage

Consommation et coûts estimés

Chaque session Claude de la machine, chiffrée d'après les prix publics, par modèle. Par session, le détail de ce qui occupe la fenêtre de contexte. Les données restent dans votre base locale.

Extensions

Des pages web isolées, branchées sur Loom

Chaque extension tourne dans sa vue web : store non persistant, CSP stricte, réseau bloqué hors des hôtes consentis. Le pont window.loom est gardé par les permissions du manifeste, les secrets vont au Trousseau.

Historique

Rien n'est perdu

Sessions archivées, historique complet et recherche plein texte (SQLite FTS5). Un plugin Obsidian résume toutes les 30 minutes ce qu'ont fait les sessions, sous ## Loom dans la note du jour.

Workflows

Une tâche en entrée, une branche relue en sortie.

L'onglet Workflows s'ouvre sur quatre gabarits prêts à lancer. Dessous, un éditeur de graphes pour composer les vôtres.

Gabarit 1 sur 4

Réaliser une tâche

EntréeUne tâche
SortieUne branche relue
  1. Plan
  2. Votre accord
  3. Implémentation
  4. Relecture ↺ 2× au plus

Un développeur propose un plan, attend votre accord, implémente. Un relecteur indépendant renvoie le travail, deux fois au plus.

Gabarit 2 sur 4

Corriger jusqu'au vert

EntréeDes tests ou un build en échec
SortieUne branche verte
  1. Reproduire
  2. Corriger
  3. Relancer ↺ 3 tours au plus
  4. Relecture

Reproduire, corriger, relancer : trois tours au plus. Un relecteur vérifie qu'aucun test n'a été affaibli.

Gabarit 3 sur 4

Relire une PR

EntréeUne PR
SortieUne review dans son onglet
  1. Analyste
  2. Exactitude
  3. Sécurité
  4. Tests
  5. Lead

Un analyste, puis trois relecteurs en parallèle (exactitude, sécurité, tests), puis un lead qui vérifie chaque retour.

Gabarit 4 sur 4

Enquêter sur un bug

EntréeUn symptôme
SortieUne cause prouvée, un plan
  1. Enquête
  2. Second avis ↺ 1×
  3. Plan de correction

Un enquêteur remonte au code, un second avis conteste l'hypothèse. Lecture seule : rien n'est modifié.

Un éditeur de graphes

Départ, contexte (PR, ticket Jira, dépôt), agents confiés à des experts, conditions, boucles bornées, validation humaine, rapport final. Étapes en parallèle, en headless ou en session visible.

Un orchestrateur par run

Une session visible reçoit chaque résultat. Elle peut questionner une étape, la relancer avec des consignes, la sauter ou arrêter le run, dans un budget.

Le coût avant de lancer

Loom estime le coût d'un run avant son départ. Ce qu'un agent construit avec vous reste une proposition tant que vous ne l'avez pas validée.

Installer

Du clone à la première session.

Aucun binaire n'est publié pour l'instant : Loom se construit avec Swift, en trois commandes. Construisez en release, car en debug le rendu du terminal est 10 à 50 fois plus lent.

  • macOS 14 ou plus récent
  • Swift 5.10
  • Claude Code (claude) installé
  • gh pour l'onglet Pull requests
$git clone https://github.com/zVasO/loom
$cd loom && swift build -c release
$swift run -c release LoomApp

Puis ⌘N pour lancer une session depuis un objectif.
