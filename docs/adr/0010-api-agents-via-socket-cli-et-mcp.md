# Une API locale pour les agents, sur le socket des hooks, servie par un CLI et un serveur MCP

Les agents hébergés doivent pouvoir agir sur Loom lui-même — poser des badges, renommer leur session, lire où ils en sont — et un orchestrateur externe doit pouvoir lister les sessions ; c'est le prérequis de l'orchestration multi-agents annoncée post-v1 (fan-out, review). Le canal existe déjà : le socket Unix de l'ADR-0005 (0600, token par session, JSON par ligne) est aujourd'hui à sens unique, agent → app, sans réponse. Décision : le même socket accepte un second type de message, une requête qui attend une réponse (`{token, request: {id, method, params}}` → `{id, result | error}`), distingué du hook par sa clé (`payload` = hook, `request` = API), si bien que `loom-hook` ne change pas. Les types de requête, le catalogue des méthodes et le client socket vivent dans un target `LoomAPI` (dépendance : LoomCore seulement), partagé par l'app et par un nouvel exécutable `loom` : un CLI (`loom badge add review`) utilisable par tout agent qui a un shell, Codex et Gemini compris, et `loom mcp`, un serveur MCP en stdio qui expose exactement les mêmes méthodes comme outils typés à Claude Code. Alternatives rejetées : un serveur HTTP local (un port ouvert pour un besoin purement local, une surface d'attaque de plus, aucun client qui en ait besoin) ; un schéma d'URL `loom://` (sans réponse, sans authentification) ; AppleScript / Shortcuts (hors de portée d'un agent CLI).

Deux portées, deux tokens. Le token de session, déjà injecté par les hooks, est aussi exposé au process de l'agent (`LOOM_SOCKET`, `LOOM_SESSION_TOKEN`) : il ne donne accès qu'à *sa* session. Un token global, généré par l'app dans un fichier 0600 de son dossier de support, donne la portée « toutes les sessions » aux orchestrateurs externes. Un token inconnu est rejeté avant toute lecture, comme pour les hooks (NFR-S).

L'API touche des métadonnées, jamais l'état. La machine à états ne connaît que quatre sources — hook, heuristique, process, utilisateur — et l'API n'en ajoute pas : un agent qui pourrait se déclarer `idle` alors qu'il bloque casserait le différenciateur de Loom. Périmètre v1, en lecture et métadonnées seulement : `session.get`, `session.setTitle`, `session.setBadges`, `badge.list`, `badge.create`, et `sessions.list` pour la portée globale. Hors périmètre, délibérément : lancer, arrêter, archiver une session, détruire un worktree, envoyer du texte dans un terminal. Tout ce que l'API permet, un agent manipulé par un fichier du dépôt (injection de prompt) le permet aussi ; le périmètre est dimensionné à ce risque, et toute extension destructive passera par une confirmation dans l'app, jamais par un simple token.

## Consequences

- Une session porte plusieurs badges (`sessionBadge`, migration v7) : `session.setBadges` remplace la liste entière, dans l'ordre donné ; le vocabulaire reste « badge », jamais « label » (CONTEXT.md).
- Les définitions de badges (nom + couleur) quittent UserDefaults pour LoomPersistence (migration v8) avant que `badge.create` existe : l'app et le CLI doivent lire la même source.
- Le protocole est versionné (`loom.version` répond la version du protocole) ; le CLI et le serveur MCP sont livrés dans le bundle et versionnés avec l'app, comme `loom-hook`.
- `HookSocketServer` garde son contrat pour les hooks et gagne un chemin de réponse ; ses tests restent sur de vrais sockets, comme aujourd'hui.
- Les mutations par l'API sont journalisées avec leur portée (token de session ou global) dans le journal existant, sans nouvelle source de transition.
- Le serveur MCP est un client comme un autre : aucune logique métier n'y vit, il traduit outil ↔ méthode et rien d'autre.
