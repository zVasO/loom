# Des extensions tierces, en pages web isolées derrière un pont à permissions

Le besoin : brancher sur Loom ce que chacun utilise autour de ses sessions — un board Jira qui lance une session depuis un ticket, une boîte Sentry, l'état d'une CI — sans que Loom ait à tout intégrer lui-même. Le cahier des charges (§2.2) excluait « un système de plugins tiers » en v1 ; cette décision revient dessus, bornée. Ce qu'une extension doit pouvoir faire, c'est afficher une interface libre, parler à un service distant, lire les sessions et proposer d'en lancer une ; ce qu'elle ne doit jamais pouvoir faire, c'est hériter des droits de l'app, qui n'est pas sandboxée (ADR-0004) et tient les clés SSH, les repos, les sessions `gh` et les cookies du navigateur intégré. Décision : une extension est un dossier (manifeste `loom-extension.json` + HTML/JS/CSS, n'importe quel framework) servi dans son propre `WKWebView` — processus WebContent sandboxé par WebKit, data store non persistant, fichiers servis par un gestionnaire de schéma `loom-ext://<id>/` confiné au dossier — et qui ne parle à Loom que par un pont, `window.loom`, dont chaque méthode est gardée côté natif par les permissions que le manifeste demande et que l'utilisateur accorde (`network` : hôtes HTTPS ; `sessions` : `read`, `launch` ; `projects` : `read`). Alternatives rejetées : des plugins natifs (bundle, dylib) chargés dans le process (le code tiers aurait tous les droits de l'utilisateur ; la library validation du Hardened Runtime les refuse de toute façon) ; des process externes XPC ou Node (accès complet au disque, et une UI à réinventer) ; JavaScriptCore sans vue (pas d'interface, or c'est le besoin) ; l'API agents et son serveur MCP seuls (ADR-0010 : parfaits pour un script ou un orchestrateur, sans UI) ; réutiliser `BrowserController` (son store `.default()` porte les cookies GitHub et Jira de l'utilisateur, et WEB-07 lui interdit toute injection de script).

Le réseau a deux verrous : l'en-tête Content-Security-Policy de chaque fichier servi (`default-src 'none'`, rien de distant, ni script, ni image, ni frame, ni connexion) et une `WKContentRuleList` fixe qui bloque tout chargement http(s) et ws(s) — si WebKit ne peut la compiler, l'extension ne se charge pas. La seule porte vers l'extérieur est `loom.http.fetch` : une `URLSession` éphémère par requête, sans cookies ni cache, HTTPS seulement, vers les hôtes du manifeste (`api.exemple.com` ou `*.exemple.com`, jamais plus large), chaque redirection revérifiée. Le pont n'écoute que la page principale de l'extension sur sa propre origine ; l'identité d'un appel est celle du handler de sa vue, jamais celle du message. Les secrets vont au Trousseau (service `app.loom.extension.<id>`), le reste dans un fichier JSON plafonné hors du dossier de l'extension.

## Consequences

- Le non-objectif « système de plugins tiers » du cahier des charges (§2.2) est révisé par cette ADR ; le reste de §2.2 tient.
- WEB-07 (aucune injection de script) et THM-09 (le contenu web n'est pas thémé) protègent les pages tierces du navigateur ; une extension est une interface de Loom, servie depuis une origine Loom, installée par l'utilisateur : le SDK y est injecté, et le thème lui est offert en variables CSS `--loom-*` qu'elle utilise ou non.
- NFR-S (« aucune donnée n'est transmise à un serveur tiers par l'app elle-même ») : l'app n'émet toujours rien d'elle-même ; le trafic de `http.fetch` est celui d'une extension que l'utilisateur a installée, vers les hôtes qu'il a acceptés, sans jamais ses cookies.
- Lancer une session reste hors de portée d'un simple jeton (ADR-0010) : `sessions.launch` n'est accepté que de l'extension affichée au premier plan, et ouvre toujours une feuille native — projet, placement, titre, badges, prompt modifiable. Rien ne démarre sans le clic de l'utilisateur. Le prompt vient de l'extension, donc souvent d'un texte écrit par un tiers (un ticket) : la feuille le dit, et c'est le garde-fou contre l'injection de prompt.
- Aucune méthode n'écrit l'état d'une session : la machine à états garde ses quatre sources. Une extension lit les sessions dans la projection de l'API agents (`APISession`) et entend leurs changements (`session.stateChanged`, `sessions.changed`) si elle a `sessions: read`.
- Le consentement porte sur le manifeste : installer ou lier montre les permissions en clair ; un manifeste qui demande davantage attend une nouvelle approbation avant de tourner ; une clé de permission inconnue refuse le manifeste (fail closed), comme une version de pont (`loomApi`) que l'app ne parle pas.
- Un process WebContent par extension ouverte, créé à la première ouverture de sa vue et gardé ensuite ; aucun avant.
- Le contrat du pont vit dans un target `LoomExtensions` (dépendances : LoomCore, LoomAPI) : manifeste, permissions, routeur, stockage, secrets, politique réseau et web, SDK — pur et testable. L'hôte WebKit vit dans LoomWeb, le câblage dans LoomApp. Le SDK est une chaîne Swift, pas une ressource : le script de release ne copie aucun bundle de ressources SwiftPM.
- Reportés : extensions d'arrière-plan, emplacements dans un projet ou une session, écriture de titres et badges, catalogue et signature, `http://localhost`, WebSocket.
