# Un navigateur propre à chaque agent, sur un profil isolé par projet, piloté par l'API agents

Le besoin : qu'un agent teste ce qu'il implémente — ouvrir son serveur de dev, cliquer, remplir un formulaire, lire la console, faire une capture — dans Loom même, sous les yeux de la personne, plutôt que de lui demander de le faire. Les navigateurs de Loom (WEB-01…07) sont ceux de l'utilisateur : store `.default()` partagé avec ses cookies GitHub et Jira (WEB-02), aucune injection de script (WEB-07). Décision : chaque session claude a son **navigateur de l'agent**, distinct des « Web n » de l'utilisateur, affiché dans le panneau latéral à côté du terminal, et piloté par des méthodes `browser.*` de l'API agents (ADR-0010, protocole v2) servies en outils MCP au format de Playwright MCP (`browser_navigate`, `browser_snapshot`, `browser_click`, `browser_type`…, réponses Markdown en sections `### Page` / `### Snapshot` / `### Modal state`) et par `loom browser <outil>`. Son stockage est un **profil web de l'agent** par projet (`WKWebsiteDataStore(forIdentifier:)`, macOS 14, identifiant dérivé de celui du projet par hachage) : un login à l'app testée survit d'une session à l'autre du projet ; une session sans projet et toute revue (onglet PR, badge `PR #n`) ont un store non persistant — du code sous revue n'hérite d'aucun profil. Ses pages reçoivent deux scripts : un crochet dans le monde de la page (console, erreurs, fetch/XHR) et un assistant dans un monde de contenu propre à Loom (`loom-agent`) qui construit l'**instantané de page** (arbre d'accessibilité en YAML, références `e12` stables tant que rôle et nom le sont, valides jusqu'à l'instantané suivant), vérifie qu'un élément est actionnable et produit les événements. Alternatives rejetées : piloter les navigateurs de l'utilisateur (ses cookies, et WEB-07) ; Playwright ou Chrome DevTools MCP lancés à côté (une installation de plus, une fenêtre hors de Loom, aucun profil par projet, rien à regarder dans la session) ; des événements natifs `NSEvent` (de confiance, mais ils rendent la fenêtre clé et volent le clavier du terminal) ; un panneau en surimpression comme le panneau Git (il masquerait la zone de saisie de claude, et les moniteurs souris du terminal prendraient les clics de la page) ; des captures en base64 sur le socket (des lignes de plusieurs Mo sur la file IPC qui porte les hooks de toutes les sessions).

Le panneau latéral **découpe** la largeur : chaque largeur que prend le terminal atteint le PTY, et claude répond à un redimensionnement en repeignant toute sa conversation. Une ouverture, une fermeture ou une fin de glisser coûtent donc un redimensionnement, jamais plus : aucune largeur animée, pas d'ajustement pendant un glisser, et le panneau ne réduit jamais de lui-même le terminal sous 80 colonnes. L'agent ouvre le panneau sur son navigateur **une fois** par pile — la première fois qu'il touche une page, et seulement si le terminal garde ses 80 colonnes — puis plus jamais si la personne le referme ; il ne change jamais l'onglet ni la session affichés.

## Consequences

- WEB-07 est révisé pour le seul navigateur de l'agent : injection de scripts, et ce que l'agent y lit (texte, stockage via `browser_evaluate`, captures) quitte la machine par son fournisseur de modèle, comme tout ce que l'agent lit. Les navigateurs de l'utilisateur restent sans injection : `BrowserController` a deux genres figés à la création, et un contrôleur d'agent sans son moteur ne crée aucune vue plutôt que de retomber sur le store de l'utilisateur.
- WEB-02 et WEB-05 décrivent les navigateurs de l'utilisateur. Les profils d'agent sont par projet (ou privés), au plus 3 vues vivantes par agent ; une session close libère les processus de son navigateur (les onglets restent à regarder), une session archivée le détruit avec ses captures. Impact NFR-M : un processus WebContent par onglet vivant d'agent.
- WEB-04 (repli `ASWebAuthenticationSession` ou navigateur système) ne s'applique jamais au navigateur de l'agent : ce serait lui donner la session Safari de la personne.
- NFR-S : l'app n'émet toujours rien d'elle-même ; le trafic du navigateur de l'agent est celui de l'agent, vers ce qu'il ouvre, avec son profil.
- ADR-0010 bornait l'API aux métadonnées ; elle s'étend au navigateur de la session elle-même, rien de plus : aucune méthode n'écrit un état, ne lance ni n'arrête de session. Les méthodes `browser.*` refusent le jeton global (`allowsGlobalScope`) : il se lit dans un fichier de l'utilisateur, tout shell d'agent y accède par `loom --global`, et il ne doit jamais piloter le profil d'un autre projet.
- Pré-autorisation : par défaut, Loom ajoute à son `--settings` les règles `mcp__loom__<outil>` de chaque outil marqué `preapprovable` dans le catalogue — jamais le serveur entier, pour qu'un outil ajouté plus tard ne soit pas autorisé en silence. C'est un nouveau canal HTTP et JavaScript hors des contrôles Bash et WebFetch de Claude Code : une page lue pendant un test peut chercher à manipuler l'agent. Ce qui le borne : le profil isolé, la politique de navigation (http, https et about:blank seulement — ni `file:`, ni `data:`, ni schéma maison, popups comprises), les revues sur profil privé, et un réglage pour revenir aux demandes de permission. Les écritures de métadonnées sont plafonnées en conséquence (titre d'une ligne de 80 caractères, badges bornés).
- L'isolement tient face aux outils, pas face à un shell sans restriction : l'app n'est pas sandboxée (ADR-0004), un processus de l'utilisateur peut lire les stores WebKit sur disque, et le jeton d'une session se voit dans `ps`. Lier un jeton à l'arbre de processus de sa session est reporté.
- Les dialogues JavaScript deviennent un état modal (`### Modal state`, `browser_handle_dialog`, ou le bandeau « <hôte> says: » du panneau) ; chaque completion WebKit est appelée exactement une fois, même à la libération d'une vue. Les événements sont synthétiques (`isTrusted` faux) : pas de `:hover` CSS ni de glisser natif ; le défilement, Tab et Entrée sont émulés. Les iframes d'une autre origine ne sont pas inspectables. Masqué, une page continue de tourner (`inactiveSchedulingPolicy = .none`) mais WebKit suspend son rendu : `### Page` le dit.
- Transport (protocole v2) : délais propres à chaque méthode, celui de l'app toujours 5 s sous celui du client ; codes `timeout` et `unavailable` ; une réponse tardive n'atteint jamais le client suivant d'un descripteur réutilisé (génération par connexion) ; SO_NOSIGPIPE des deux côtés. Les captures sont écrites (0600, dossier 0700 exclu des sauvegardes) sous `agent-browser/screenshots/` à côté du socket ; le serveur MCP les lit là et nulle part ailleurs, et les rend en bloc image.
- ATS : `NSAllowsArbitraryLoadsInWebContent` dans l'Info.plist de la release — les vues web chargent http (un serveur de dev, 127.0.0.1 compris), `URLSession` reste en HTTPS. La barre d'adresse ouvre `localhost:5173` en http, pour l'utilisateur comme pour l'agent.
- Le moteur vit dans LoomWeb (`AgentBrowser/`, qui dépend désormais de LoomAPI pour la correspondance méthode → commande), ses scripts en chaînes Swift testées par Node sur un vrai DOM (`Tests/AgentBrowserJS/`) ; le câblage dans LoomApp. Reportés : envoi de fichiers, remplissage de formulaire en un appel, captures pleine page, préréglages de largeur de viewport, mode « sites locaux seulement », nettoyage des profils d'un projet retiré.
