# Le thème de Loom appliqué à Claude Code, par son dossier de thèmes

Loom peint le terminal avec sa palette (fond, texte), mais Claude Code dessine par-dessus avec son propre thème, `dark` par défaut, sans rapport avec la famille choisie ni avec l'apparence : fonds des messages, diffs, bordures et accent jurent, surtout en clair. Son mode `auto` n'aide pas : il demande le fond au terminal (OSC 11), et SwiftTerm, sans couleurs configurées, répond les siennes. Claude Code (2.1.118 et plus) lit des thèmes personnalisés dans `~/.claude/themes/<slug>.json` (`name`, `base`, `overrides` de ses jetons de couleur), les choisit par le réglage `theme: "custom:<slug>"` — valable dans tout fichier de réglages, donc dans le `--settings` en ligne de l'ADR-0005 —, surveille ce dossier et recharge un fichier modifié sans redémarrer. Décision : **sur option, désactivée par défaut**, Loom écrit ses thèmes dans ce dossier (`$CLAUDE_CONFIG_DIR/themes` sinon `~/.claude/themes`) et chaque session qu'il lance reçoit `theme` avec ses hooks. Un thème **vivant par projet** (`loom-project-<8 hex de l'UUID>.json`, « Loom · <projet> »), plus `loom.json` pour une session sans projet : le nom ne change jamais, le contenu est la famille du projet (son override, sinon la globale) dans la variante de l'apparence courante ; changer de thème, d'override, d'apparence (ou macOS qui bascule) réécrit le fichier, et les sessions ouvertes suivent en direct. Un **catalogue** (`loom-<famille>-dark|light.json`, familles intégrées et importées) rend chaque variante choisissable à la main dans `/theme`, hors de Loom aussi. La correspondance des jetons est une fonction pure (`ClaudeThemeExport`) : l'accent pour la marque, les états pour succès, erreur, avertissement et mode plan, les surfaces pour les fonds de messages, les diffs comme couleurs d'état fondues dans le fond du panneau ; `base` suit la clarté de la palette, pour que tout jeton non couvert reste lisible. Alternatives rejetées : passer `theme: "light"`/`"dark"` seulement (corrige le clair/sombre, pas les couleurs, et ne suit pas un changement en cours de session) ; répondre à OSC 11 avec la palette de Loom pour que `auto` devine juste (même limite, et reste possible à part) ; écrire `theme` dans `~/.claude/settings.json` (toucherait les sessions lancées hors de Loom).

## Consequences

- Entorse assumée au principe « rien d'écrit chez l'utilisateur » (STA-01, `docs/research/claude-code-hooks.md` §3) : d'où l'option, désactivée par défaut, et un périmètre borné aux seuls fichiers aux noms de Loom (`loom.json`, `loom-project-xxxxxxxx.json`, `loom-…-dark|light.json`). Un fichier à l'utilisateur portant par hasard un nom du catalogue serait réécrit ou retiré.
- Un fichier n'est réécrit que si son contenu change : chaque écriture recharge le thème de toutes les sessions qui le suivent.
- Désactiver l'option retire tous ces fichiers et Loom cesse de passer `theme` ; une session encore ouverte garde `custom:loom-…` jusqu'à sa relance (ce que Claude affiche quand le fichier disparaît n'est pas documenté) ; relancée, elle reprend le thème de l'utilisateur.
- `theme` passé par `--settings` l'emporte sur celui des réglages de l'utilisateur pour les sessions de Loom ; un `/theme` fait dans une session n'y survit pas à une relance tant que l'option est active.
- Le dossier est créé dès que l'option est active (au lancement de Loom, ou quand on l'active), avant toute session qui s'en sert : Claude ne surveille qu'un dossier qui existait à son démarrage. Option désactivée, Loom n'y crée rien.
- Hors périmètre : la palette ANSI 16 couleurs par thème du terminal (THM-04), qui reste fixe.
