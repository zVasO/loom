# Une session se lit aussi comme une conversation : une seconde vue de la même session native, jamais une seconde source

Dans l'onglet Sessions, une session ne se voyait que par son terminal — l'interface de claude, faite pour agir. Pour relire, elle sert mal : le Markdown y reste du texte (un tableau en barres verticales, un lien qu'on ne clique pas), une longue réponse part dans le défilement, la sélection se fait à la cellule, et chaque redimensionnement fait repeindre toute la conversation. On veut lire ce que claude a répondu comme on le lit dans une app de chat — Markdown rendu, appels d'outils repliés — et lui répondre de là. Sans que Loom devienne un second client de claude : il héberge l'agent, il ne le remplace pas.

## Décision

**La vue conversation est une seconde vue de la même session, pas une seconde session.** Un sélecteur « Terminal | Chat » dans l'en-tête de la session (⌘⇧M, menu View › Show Session as Chat) montre, à la place du terminal et dans le même cadre, la conversation de la session native. Le mode est tenu par session dans le modèle (`AppModel.sessionViewModes`, `SessionViewMode.swift`) — la vue de détail est reconstruite à chaque changement d'onglet — et une session jamais basculée prend le dernier mode choisi (`loom.session.viewMode`).

**Elle se lit dans le fichier de claude, et nulle part ailleurs.** `ClaudeConversation` (LoomAgents) lit le `~/.claude/projects/<dossier>/<uuid>.jsonl` de la session native — celui que `claude --resume` relit — et en tire des `ConversationEntry` (LoomCore) : un message de l'utilisateur, une réponse de claude en Markdown, sa réflexion quand le fichier la donne en clair, un appel d'outil avec son résultat, une notice (commande slash, compaction, interruption). Ces fichiers atteignent des mégaoctets : `ClaudeConversation.Reader` ne lit que ce que le fichier a gagné depuis la dernière fois, hors de l'acteur principal. `SessionChatPane` l'interroge chaque seconde tant que le process vit, toutes les 400 ms pendant que claude travaille, une seule fois pour une session terminée. Loom n'en garde aucune copie : rien à synchroniser, rien qui puisse dire autre chose que le terminal.

**Le terminal reste l'endroit où claude tourne, et où l'on répond aux permissions.** Le champ de la vue conversation n'appelle aucune API : ce qu'on y écrit est tapé dans le terminal de la session, en un collage entre crochets (`KeyTranslator.paste(_:bracketed:)` — les retours à la ligne restent un seul message) suivi de Retour. Session au repos : par `submitWhenReady`, qui attend l'invite de claude. Session au travail : tout de suite — claude met en file ce qu'on lui tape pendant qu'il travaille. Une session `needs_input` est soit une question posée en fin de tour, à laquelle le champ répond, soit une demande de permission, que seul le terminal dessine et à laquelle un collage suivi de Retour répondrait. L'état ne les distingue pas, le journal des transitions si (`Stop · question` contre `PermissionRequest`, lu par `AppModel.sessionWait`) : sur une permission, le champ n'envoie rien et un bandeau ramène au terminal. Une demande laissée sans réponse ne reste d'ailleurs pas forcément `needs_input` : passé la fenêtre de priorité des hooks, le silence du terminal suffit à l'heuristique pour ramener l'état à `idle`. `sessionWait` passe donc sur ce qui a été deviné d'un écran immobile, et la demande tient tant que l'appel d'outil qu'elle concerne n'a pas de résultat dans la conversation. La question est reposée au journal à l'instant d'envoyer.

**La conversation se remplit bloc par bloc.** claude écrit une ligne par bloc de contenu — un texte, un appel d'outil, un résultat — une fois le bloc terminé, et avec un peu de retard sur l'écran. La vue montre donc une réponse quand elle est écrite, pas jeton par jeton ; pendant ce temps, elle dit que claude travaille. Qui veut le voir écrire bascule sur le terminal.

**La vue remplace le terminal, elle ne le recouvre pas.** `SessionDetailView` monte `SessionChatPane` à la place de `TerminalPane`, sans transition. La surface du terminal appartient au modèle : au retour, le volet la repeint comme après un changement d'onglet, et son premier ajustement — même cadre, même grille — est écarté par le runtime. Ni redimensionnement, ni conversation repeinte par claude. Le panneau Git et le panneau latéral restent ce qu'ils étaient.

Alternatives rejetées : lire l'écran du terminal — on n'y retrouve ni le Markdown d'origine, ni ce qui a défilé, ni la frontière entre un appel d'outil et son résultat, et chaque version de claude le dessine autrement ; piloter claude par son SDK ou par `stream-json` à la place de son interface — on aurait le jeton par jeton, mais Loom deviendrait un second client : permissions, menus et commandes slash à refaire, et une session qui n'est plus celle qu'on reprend dans un terminal ; garder le terminal monté sous la vue conversation — ses moniteurs d'événements valent pour toute la fenêtre : il prenait les clics et la molette de ce qui le recouvrait, et le clavier dès que rien ne le tenait.

## Consequences

- Ce que la vue conversation ne montre pas, ou ne fait pas : les dialogues de permission (un bandeau et « Open terminal ») ; les menus des commandes slash et les sélecteurs de claude (`/model`, `/resume`) — une commande tapée dans le champ part comme un message collé ; les images, réduites à `[image]` ; les échanges propres aux sous-agents, écrits dans d'autres fichiers — on voit l'appel de l'outil et ce qu'il a rendu ; l'interruption d'un tour (Échap), qui se fait dans le terminal.
- Une conversation reprise (`/resume`) ou vidée (`/clear`) dans le terminal est suivie : la vue lit `AppModel.nativeSessionID(for:)` et repart du nouveau fichier.
- Un terminal secondaire n'a pas de conversation : pas de sélecteur, toujours son terminal. Le tiroir de l'onglet PRs garde le terminal de la session de review.
- Le fichier n'existe qu'au premier message : avant, la vue est vide et le dit, et le premier message peut partir de son champ.
- Tant que la vue conversation est affichée, le terminal n'est pas monté et ne s'ajuste pas : une fenêtre ou un panneau latéral redimensionnés entre-temps coûtent un seul redimensionnement au retour.
- Sans hooks, une attente devinée par l'heuristique (`prompt`) n'est pas une question connue : le champ n'envoie pas. Dans le doute, on ne tape pas.
- Le format du fichier n'est pas un contrat de claude : la lecture ignore ce qu'elle ne connaît pas. S'il change, la vue montre moins ; le terminal, lui, ne dépend de rien de tout cela.
- `endedOnQuestion`, écrit pour les workflows (ADR-0021 : « on ne tape jamais par-dessus une question ou une demande de permission »), passe de `WorkflowRunner` à `AppModel`, au-dessus de `sessionWait` : une seule lecture du journal pour les deux.
- Une permission refusée ne laisse aucun signal — claude n'émet pas de `Stop` après une interruption : le bandeau reste le temps que l'état retombe à `idle`, puis le champ envoie de nouveau, l'appel refusé ayant son résultat.
- La tournée des thèmes (ADR-0022) a un écran `chat` ; son claude de remplacement écrit une conversation inventée dans `~/.claude/projects/loom-theme-tour/`, là où Loom cherche — le seul fichier qu'elle laisse hors de `LOOM_SUPPORT_DIR`.
