# Des workflows qui livrent : une tâche en entrée, une branche en sortie

Les workflows (ADR-0017 à 0020) savaient lire et rapporter : un graphe dessiné à la main, des étapes en lecture seule dans le dossier du projet, un rapport HTML à la fin, et depuis une bibliothèque vide. Trois défauts en découlaient. **Rien ne se lançait sans avoir d'abord tout construit** — experts, étapes, prompts, champs — pour un résultat qu'on ne connaissait pas. **Rien n'était produit** : une étape qui écrit travaillait dans le dossier du projet, à côté de ce que la personne y faisait, donc on n'écrivait pas. **Chaque étape repartait de zéro** : un agent qui planifie, un autre qui implémente, un troisième qui corrige, chacun relisant le dépôt et aucun ne sachant ce que l'autre avait appris. On veut qu'un workflow fasse le travail d'une session bien menée — planifier, écrire, faire relire, corriger — sans qu'on la mène.

## Décision

**Un run peut travailler sur sa propre branche.** `Workflow.workspace` vaut `project` (comme avant : le dossier du projet, ou le checkout en lecture seule d'une PR) ou `worktree` : le run crée un worktree sur une branche `loom/<tâche>` à son démarrage, par le même chemin que les sessions (`<repo>-worktrees/`), et toutes ses étapes y travaillent. Le dossier du projet ne bouge pas, rien n'est poussé. Ce que le run laisse, c'est cette branche : son nom, ce qui y a changé (`RunChanges`, mesuré contre le commit de départ, commité ou non), et une session qu'on ouvre dedans pour relire le diff, commiter, pousser, ouvrir la PR — les actions qu'une session a déjà. Un workflow sur branche ne charge pas de PR (son checkout est en lecture seule) : le validateur le refuse.

**Un run part d'une tâche.** `RunInputs.task`, citée par `{{run.task}}` : ce qu'il y a à faire, dans les mots de la personne. Un workflow qui la cite la demande au lancement, et ne démarre pas sans. Elle nomme le run dans les listes et sa branche. `{{run.branch}}` et `{{run.base}}` donnent aux étapes de quoi lire ce que le run a changé (`git diff {{run.base}}`).

**Une étape peut poursuivre une conversation.** `AgentConfig.continues` nomme une étape d'avant, ou l'étape elle-même : au lieu d'un nouvel agent, la suite est tapée dans la même session (étape visible) ou reprise par `claude -p --resume` (étape headless). C'est ce qui fait d'un plan, d'une implémentation et d'une correction le travail d'un seul développeur, pendant que le relecteur, lui, reste un regard neuf à chaque tour. Les conversations sont gardées dans `RunState.conversations`, hors des enregistrements d'étape qui repartent à zéro à chaque passe. Règles : même mode que l'étape poursuivie, qui doit s'exécuter avant ; jamais deux étapes d'une même conversation côte à côte ; pas dans un « pour chaque ». Une session fermée, occupée ou qui attend la personne depuis trois minutes n'est pas forcée : l'étape ouvre la sienne — on ne tape jamais par-dessus une question ou une demande de permission.

**Loom propose des gabarits, sans rien installer.** `WorkflowTemplates` : Réaliser une tâche (plan, ton accord, implémentation sur branche, relecture indépendante qui renvoie le travail), Corriger jusqu'au vert, Relire une PR, Enquêter sur un bug. La bibliothèque démarre toujours vide (le choix d'avant tient) : un gabarit est une offre dans la galerie, copiée dans la bibliothèque quand on le lance ou qu'on l'ouvre, avec ses experts. Les étapes qui écrivent sont des **sessions visibles** : on les suit dans Sessions et Mission Control, elles demandent leurs permissions comme toute session. Les étapes qui jugent restent headless, avec un expert en lecture seule.

**Un run se lit comme une liste.** L'onglet montre chaque étape dans l'ordre où le run l'atteint (`WorkflowOutline`) : son état, sa passe, son verdict, sa durée, sa réponse ; en tête, la tâche, la branche et les changements. Le graphe reste à un clic. La feuille de lancement ne demande que ce que le workflow lit — la tâche, une PR, un ticket — et dit où le run travaillera avant qu'il parte.

Alternatives rejetées : laisser les étapes écrire dans le dossier du projet (deux mains dans le même dossier) ; un worktree par étape (rien ne s'additionne) ; une seule longue session pilotée par un prompt (rien d'observable ni de borné, pas de regard indépendant) ; des workflows livrés d'office dans la bibliothèque (défaits au commit `d63c052` : on ne remplit pas la bibliothèque de quelqu'un).

## Consequences

- `Expert.workTools` (lecture, édition, shell) n'est jamais un défaut : seul l'expert « Développeur » des gabarits le porte, et une étape headless sans expert ne l'a que dans le worktree d'un run. Les règles de l'ADR-0020 tiennent : un agent ne donne pas d'outils d'écriture à un expert sans qu'on le lui demande.
- Le worktree d'un run n'est pas supprimé avec le run : c'est du travail. Il se retire comme celui d'une session, depuis la session qu'on y ouvre.
- Les runs, workflows et bundles d'avant se lisent tels quels : `workspace` absent vaut `project`, une valeur inconnue aussi ; un run sans `task`, `worktree` ni `conversations` se décode.
- La référence du format (`loom_library_reference`) décrit `workspace`, `continues` et `run.*` ; `loom_library_run_request` accepte une tâche — une session peut ouvrir la feuille de lancement préremplie.
- Le commentaire d'une validation humaine arrive à l'étape renvoyée (« ↺ à revoir »), comme la raison du verdict d'un agent.
- Les sessions d'un run sur branche portent son worktree : panneau git et actions d'envoi y fonctionnent.
