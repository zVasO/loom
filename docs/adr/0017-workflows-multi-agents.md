# Des workflows multi-agents : un graphe dessiné, un moteur pur, des experts Claude Code

Une review de PR faite par un seul agent mélange tout : le besoin, le code, PHP, Symfony, la sécurité, les tests. On veut un **workflow** : un graphe nommé, dessiné dans Loom, dont chaque étape est confiée à un **expert** d'un seul domaine, avec ses **connecteurs** (Jira, serveurs MCP) et ses **skills**, dispatché en parallèle, revu par un contrôle de cohérence qui relance la boucle — deux fois au plus —, et un **artefact** HTML à la fin. Les workflows ne se limitent pas aux reviews. Décision : **le modèle et ses règles dans un package pur, `LoomWorkflows`** (graphe, validateur, planner, gabarits, schéma des réponses, estimation, bibliothèque sur disque, gabarit du rapport), testé comme `ReviewSchedulePlanner` ; **l'exécution dans `LoomApp`** (`WorkflowRunner`), qui a les sessions, les PR et claude ; **l'éditeur en React Flow**, une page embarquée hors ligne servie par `loom-workflows://`, parce qu'un éditeur de graphe natif en SwiftUI coûterait plus que tout le reste. Le parallélisme se lit dans les arêtes (plusieurs sorties : dispatch ; plusieurs entrées : attente de toutes) ; une boucle n'est pas une arête mais un nœud qui nomme les étapes qu'il relance, **toujours bornée** (0 à 5 passes de plus) et arrêtée plus tôt par une condition sur une sortie structurée, jamais sur du texte libre. Les étapes ne se passent pas des conversations mais des **réponses JSON validées** contre leurs champs, relancées une fois quand elles ne collent pas ; une étape nomme ce qu'elle lit par `{{steps.x.champ}}`, `{{previous.x}}` (la passe d'avant), `{{pr.*}}`, `{{ticket.*}}`. Un expert devient des options de Claude Code, pas un format maison : `--append-system-prompt` (ses instructions et le `SKILL.md` des skills de l'étape — c'est ainsi qu'une skill « se déclenche à un endroit »), `--mcp-config` + `--strict-mcp-config` (ses connecteurs ; pas de strict quand un connecteur est un serveur déjà configuré dans Claude Code, l'Atlassian distant connecté en OAuth), `--allowedTools` (lecture seule par défaut : un run headless n'a personne pour répondre à une demande de permission). Chaque étape tourne en **headless** (`claude -p`, par défaut) ou dans une **session visible** de Loom qui écrit sa réponse dans le dossier du run. Le ticket Jira est lu **par claude à travers un connecteur Atlassian**, pas par un client REST de Loom. Le rapport porte **un thème de Loom**, ses couleurs mappées par rôle, plus un volet « document » optionnel (polices, rayon, logo) — pas un système de thèmes à part. Alternatives rejetées : des sous-agents Claude Code orchestrés par un agent chef dans une seule session (rien d'observable, rien de borné, le contexte qui gonfle) ; un moteur de workflows tiers (n8n, Temporal : un service à faire tourner pour une app de bureau) ; un éditeur natif ; laisser les étapes se passer leurs transcripts.

## Consequences

- Les fichiers : `<support>/workflows/{workflows,experts,connectors}/<id>.json`, lisibles et exportables (un workflow s'exporte avec ses experts et connecteurs, jamais un secret) ; les runs dans `<support>/workflow-runs/<id>/` (`run.json` réécrit à chaque pas, `log.txt`, les réponses des étapes visibles, `artifact.html`). Un run coupé par un arrêt de Loom est relu comme `interrupted`.
- Les secrets des connecteurs vont au Trousseau, sous `connector.<id>`, l'espace des extensions réutilisé ; un connecteur les référence par `{{secret:CLE}}`.
- Le bundle de l'éditeur est versionné (`Sources/LoomApp/WorkflowEditor`) : l'app se construit sans Node ; la CI vérifie qu'il correspond à `WorkflowEditor/src` et le fait tourner sur un vrai Chromium. On le reconstruit par `scripts/build-workflow-editor.sh`.
- Le validateur Swift fait foi : l'éditeur l'appelle à chaque enregistrement et affiche ses problèmes sur les nœuds ; le bouton Run reste éteint tant qu'une erreur reste.
- Une estimation (nombre de runs claude, ordre de grandeur en dollars par `ModelPricing`) est montrée avant chaque lancement ; le coût réel, rapporté par claude, est sommé sur le run.
- Le worktree d'une PR reste en lecture seule (gardes de l'ADR-0014) ; les sessions visibles qui y tournent sont marquées comme exécutant du code non fiable.
- Une review planifiée peut lancer un workflow sur chaque PR choisie ; l'artefact peut remplir l'onglet de la PR (résumé, commentaires en attente ancrés sur le diff, verdict suggéré) par le même chemin que les reviews planifiées.
- Le rapport est un HTML autonome : ses données en ligne, son script en ligne, rien de chargé sauf la feuille de polices Google du thème ; le texte des réponses n'est jamais inséré comme HTML.
